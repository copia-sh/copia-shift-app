# シフトアプリ機能・UI改善計画

作成日: 2026-09-16  
状態: 調査・計画作成完了／実装未着手  
対象: `copia-shift-app` の現行ワークツリー（HEAD: `9807973` と作業中の差分）

## 1. 結論

最初に着手すべきなのは、カレンダーの情報欠落と編集操作の不確実さを解消し、「見る・入力する・確定する」を分かりやすくすることです。その上で、提出状況、定型入力、確定後の変更申請を追加します。

現状でも、複数枠、一括操作、表示フィルター、書き出し、外部連携の実装があります。これらを新機能として作り直す必要はありません。課題は、機能が存在していても入口が分かりにくいこと、表示によって情報量や操作の意味が変わること、提出から変更対応までの業務がアプリ内で完結しないことです。

推奨する順序は次のとおりです。

1. 表示と保存の正しさを保証する。
2. 画面上の情報と操作を、利用目的に沿って配置し直す。
3. 繰り返し入力と提出確認の手間を減らす。
4. 確定後の変更、履歴、必要な通知をつなぐ。
5. 必要人数との比較など、運用要件に依存する機能を追加する。

本書の効果は設計上の仮説です。利用時間や誤操作率の改善を実測したものではありません。実装時に同じ課題を改善前後で操作して検証します。

## 3. 設計の軸

### 3.1 利用目的を画面構成の基準にする

| 利用者 | 最初に知りたいこと | 主操作 |
|---|---|---|
| メンバー | 次の自分のシフト、希望の提出状況、確定後の変更 | 希望入力・提出・変更申請 |
| リーダー | 誰が未提出か、何が未確定か、変更申請があるか | 対象確認・確定・差し戻し |
| 管理者 | 上記に加え、メンバー・設定・連携状態 | 運用設定・管理 |

これは現行権限から導いた利用仮説です。専任のシフト作成者がいるか、希望を「提出」して締め切る運用かは未確定です。役割で画面を強制固定せず、本人が選んだ表示を保存します。

### 3.2 UIの基本原則

- 同じシフトは、どの表示でも同じ内容として見える。
- 通常のタップは詳細表示。編集は明示的な入力から始める。
- 表示対象・期間・編集対象を、操作の直前に確認できる。
- 閲覧できる情報を、編集不可という理由だけで薄くしない。
- よく使う操作を常設し、管理・連携・説明は必要な場所から開く。
- 色は勤務種別、状態バッジは希望／確定、外枠は選択状態に使い、意味を分担する。
- 人数増加を文字の縮小で吸収せず、要約・絞り込み・詳細表示で対応する。

## 4. 推奨する画面と機能配置

### 4.1 PC

```text
[グループ名 ▼]                  [書き出し] [管理 ▼] [自分の名前 ▼]
[シフトを見る] [希望を入力] [確定・調整 ※権限あり]

[前へ] [2026年9月／9月14日〜20日] [次へ] [今日] [一覧｜月｜週]
[全員｜自分] [氏名検索] [属性 ▼] [状態 ▼] [条件解除]
表示対象 12人・希望のみ                         [凡例]

[必要な案内：未提出／確認待ち／変更あり。押すと対象へ]

[カレンダー／一覧                       ] [選択した日・人の詳細]
[                                      ] [時間枠・状態・履歴   ]
[                                      ] [編集／確定など       ]

複数選択時のみ：[3日・2人・5枠を選択] [操作] [選択解除]
```

- 上段には所属と補助機能、次段には作業目的、その下には期間と表示条件を置く。設定やログアウトを日常の入力と同じ重さで並べない。
- 「管理」にメンバー・グループ設定・連携状況を集約する。リーダーには権限のある項目だけ表示する。
- 名前メニューにプロフィールとログアウトを置く。現在の「書き出し」は独立した入口を維持する。
- 個別の詳細・編集は右パネルを基本とし、比較中のカレンダーを隠しすぎない。横幅が不足する端末ではシート表示に切り替える。
- 上部の固定領域は期間・表示条件を中心とした最小限とし、全ヘッダーを固定して表示面積を消費しない。
- 「確定・調整」は管理専用の別アプリにせず、同じカレンダーに確認対象と操作を追加する構成にする。

### 4.2 スマートフォン

```text
[グループ名 ▼]                             [メニュー]
[シフトを見る｜希望を入力｜確定・調整 ※権限あり]
[前へ] [2026年9月] [次へ] [今日]
[一覧｜月｜週]       [自分／全員] [絞り込み・適用数]

[次の自分のシフト／提出状況 ※必要時のみ]
[コンパクトな月カレンダー、または日付の選択帯]
[選択日の詳細：氏名・全時間枠・種別・状態]

編集中のみ下部シート：[日付・対象者] [入力欄] [保存]
複数選択中のみ下部バー：[選択数] [操作を開く] [解除]
```

- 月表示は「小さな月カレンダー＋選択日の詳細」を推奨する。現状の日別カードを1か月分縦に並べる方式は、必要なら「一覧」の表示方法として残す。
- 初回はメンバーの自分表示を推奨するが、全員表示への切替は常に見せる。管理者・リーダーはチーム表示を初期候補とし、2回目以降は保存した条件を優先する。
- 多数の属性チップを横に流し続けず、よく使う条件と適用中条件を見せ、残りを絞り込みシートに収める。
- 下部に常設ナビゲーションと大きな操作バーを重ねない。操作バーは1行の要約から展開し、`safe-area-inset-bottom` と表示中の高さに応じて本文の余白を取る。
- 単日の編集では「種別」「時間」「保存」を縦に配置する。6種類の種別と時刻入力を横1行に押し込まない。

### 4.3 表示ごとの役割

| 表示 | 役割 | 改善後の仕様 |
|---|---|---|
| 一覧 | 複数人×複数日の比較・一括入力 | 氏名列・日付を固定。標準／コンパクトを選択可能。横スクロールは表の中だけ |
| 月 | 月全体の見通し・日付選択 | 少人数・自分は枠を表示。多数人は日別人数・未回答・注意事項を要約し、詳細で全員を見る |
| 週 | 時間帯の重なりを確認 | 設定された週開始曜日に沿った7日間。前後移動は7日、月境界も連続。モバイルは週の日付帯＋選択日の時間軸 |

現在の月全体を横に並べる時間軸を日常的に使っている場合は、削除前に利用を確認し、「時間軸（月）」として補助表示に残す。単に「週」のラベルを変えるだけでは、7日単位で確認する目的を満たさない。

## 5. 既存機能の改善

P0: 情報欠落・誤更新・復旧困難を先に解消。P1: 日常操作の中心として次に実装。P2: 運用要件と利用結果を確認して追加。

### I-01 複数枠を欠落なく表示・操作する［P0］

- 現状: PC・モバイルの週表示は、時間指定枠から確定を優先して1枠を選んで描画する。一括操作もセルの代表状態から対象を判定している。
- 改善: 全時間枠を各時刻に描画する。個人内の複数枠と人同士の並列表示を区別し、各枠から詳細を開く。一括確定は選択セル内の「確定可能な希望枠」を抽出し、確定済み・不可・対象外を件数付きで示す。
- 効く理由: 表示を切り替えるだけで予定が消えると、利用者は誤った空き時間を判断する。データの単位である「枠」を表示と操作でも保つことで、欠落と誤った一括変更を同時に防げる。
- 完了条件: 同日・同一人の2〜6枠を全表示で照合できる。希望と確定が混在していても希望枠だけ確定できる。日数・人数・枠数を混同しない。
- 対象: `ShiftMatrixViews.tsx`、`shiftVisual.ts`、`App.tsx`。

### I-02 タップ即変更を、詳細表示と明示的編集に分ける［P0］

- 現状: 通常モードで単純な自分のセルを押すと、種別が循環してすぐ保存される。詳細な時間編集はセル選択後の下部バーにある。他人・確定済みセルは操作できず、詳細確認の入口も乏しい。
- 改善: タップで詳細を開き、編集可能な場合に「編集」を表示する。空欄では日付入りの入力シートを開く。複数選択は「まとめて入力」から明示的に開始する。高速な循環入力は必要なら後から任意設定にする。
- 効く理由: 「見るつもり」と「変えるつもり」を同じ入力に割り当てないことで、記憶すべきモードと誤操作を減らす。確定済みでも詳細を読めるようになる。
- 完了条件: 閲覧タップは書き込み0件。日付・人・全枠を確認して保存でき、キャンセルでは更新されない。権限外の更新ボタンは表示しない。
- トレードオフ: 1日の単純入力は操作数が増える。I-03の一括入力とN-02のテンプレートで繰り返し作業を減らす。

### I-03 一括更新・複数枠保存の信頼性［P0］

- 現状: `applyOps` の更新は複数の独立書き込み、枠編集は更新・新規作成・削除の順に実行する。途中失敗時は一部だけ反映し得る。`handleBulk` は失敗でも一部の操作で選択を解除する。セルへの入力は `busy` を直接参照しない。
- 改善: 1日分の枠編集は全体検証後に単位をまとめて保存する。一括操作は成功・失敗・対象外を返し、失敗対象の選択を残す。保存中は対象への再操作を抑止し、重複生成を防ぐ。期間・表示・絞り込みを変更したら選択を解除するか、画面外対象を明示する。
- 改善: 通常の複数枠に同一時刻を一括適用して重複させない。適用後の全枠を検証し、不正なら保存前に止める。入力値の妥当性はUIだけに依存させず、ルール／信頼できる書き込み層でも保証する。
- 効く理由: 利用者が考える「1回の保存」とシステムの更新単位を近づけることで、半端な結果と再試行による二重登録を防ぐ。UIが速く見えてもデータを信頼できなければ業務は短縮しない。
- 完了条件: 連打、途中エラー、競合、月移動後の操作で、隠れた日付の意図しない更新や重複がない。エラーは開いている編集画面内に表示され、入力を保持する。
- 技術方針: 上限内の原子的な書き込み、競合検知用revision、操作IDを検討。大規模操作を分割する場合は全体が原子的とは表示しない。「元に戻す」は競合がない場合だけ成立する設計にする。

### I-04 週表示の期間・日付移動を一致させる［P1］

- 現状: `ShiftWeekView` は `daysOfMonth` を使い、前後移動も月単位。「週」から通常想定する範囲と異なる。
- 改善: 第4章の7日表示を実装。週の期間ラベル、前週・翌週・今週への操作を設け、必要な月境界データも購読する。
- 効く理由: ラベル、表示範囲、移動単位が一致すれば、利用者が現在地を読み替える必要がなくなる。
- 完了条件: 日曜／月曜始まり、月末・年末をまたぐ週で正しい7日を表示し、移動後に選択対象が持ち越されない。

### I-05 画面密度と視覚的な優先順位［P1］

- 現状: 月表示では未回答のセルも人数×日数分並ぶ。週表示では氏名の先頭2文字や8〜9pxの時刻を使い、操作不可の予定を低い不透明度で表示する。モバイル月表示は日別カードが縦に連続する。
- 改善: 月は人数に応じて要約、週は表示人数を絞って読む設計にする。氏名は省略しても詳細で全文を取得可能にする。通常の説明・入力は14〜16px程度、補足は12px程度を設計目標とし、時間情報を8pxまで縮めない。
- 改善: 青系の基調を維持し、ボタンの影・太字・枠線を整理する。主操作は1つを強調し、未回答は静かな表示、確定／希望はラベルと形でも区別する。勤務色と個人色の意味を混在させない。
- 効く理由: 空欄と補助操作の視覚的な強さを下げると、視線を探している予定へ向けやすい。読める情報量を超えた場合は要約する方が、全情報を極小表示するより判断を維持できる。
- 完了条件: 1・6・12・30人、長い氏名、6種別、複数枠で破綻しない。編集不可の予定も読むことができ、PCとスマホで必要情報へ到達できる。

### I-06 フィルター・日付選択・表示設定［P1］

- 現状: 自分・全員・属性ORのフィルターは実装済み。ビューとフィルターは画面のstateで、氏名・状態検索の入口はない。
- 改善: 氏名検索、希望／確定／未回答の状態フィルター、月・日付の直接選択を追加する。グループ・ユーザーごとに表示方法と条件を保存し、「解除」を常設する。属性ORの意味は維持して表示する。
- 効く理由: 繰り返し同じ範囲へ絞る操作と、前後ボタンの連打を減らす。条件が見えることで「予定が消えた」という誤解も減る。
- 完了条件: 条件変更で表示人数が更新され、0件では条件解除を案内する。別グループ・別ユーザーへ条件が誤適用されない。未回答の判定は対象期間・対象メンバーに対して行う。

### I-07 ダイアログ・操作対象・状態表示［P1、保存失敗表示はP0］

- 現状: 編集・書き出し等は固定配置のdivを使い、共通のフォーカス制御は確認できない。保存失敗は主画面に出るため、ダイアログの背後に隠れ得る。シフト購読は成功コールバックのみで、読み込み失敗をUIへ渡していない。
- 改善: 共通Dialog／Sheetでタイトル、初期フォーカス、Tab移動、Escape、閉じた後のフォーカス復帰を実装する。送信失敗は操作箇所に表示。読み込み中・0件・権限エラー・通信失敗・保存中・保存済みを区別する。
- 改善: 矢印に「前の週」等の名前を付け、時刻入力にラベルを付ける。主なタップ対象は44px程度を目標にする。固定バーでフォーカス位置が隠れないようにする。
- 効く理由: 操作の結果と次の行動が同じ場所で分かれば、待ち続ける・連打する・入力をやり直す行動を減らせる。キーボードやタッチでも同じ操作経路を使える。
- 完了条件: キーボードのみで開閉・入力・保存ができる。失敗後も値を保持して再試行できる。375px幅と拡大表示で操作欄を利用できる。
- 基準: WCAG 2.2の最小ターゲットは原則24×24 CSS pxで例外条件がある。44pxは本計画の操作性目標であり、AA要件の数値と混同しない。[W3Cの解説](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)、[モーダルの実装指針](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)、[フォーカスを隠さない基準](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)。

### I-08 書き出しと外部連携の入口［P1／連携状況はP2］

- 現状: ICSと月次Excelコピーには条件・件数の表示がある。状態の初期値は希望・確定の両方で、詳細設定内にある。購読は実装済みだが入口非表示。Sheets同期は別の用途として存在する。
- 改善: 書き出し画面の上部に「自分・対象期間・希望／確定・件数」の要約を常時表示し、出力内容を数件プレビューする。Excelは対象月と1日セルから貼る形式を保つ。状態の初期値を変える場合は既存運用を確認する。
- 改善: 管理メニューの連携状況に、利用可能な連携だけを表示する。同期の最終成功時刻・対象期間・失敗を、認証された読み取り経路から取得する。資格情報はブラウザへ渡さない。
- 効く理由: 出力前に範囲を確かめられると、希望を確定予定として扱う誤解や貼り付けミスを減らせる。連携の鮮度が見えれば、登録漏れと同期遅延を切り分けられる。
- 完了条件: プレビューと実出力が一致し、0件・古い種別・複数枠を説明できる。購読の非表示方針を維持する。Sheetsの既存同期処理を唯一の書き込み経路として扱う。

### I-09 管理画面と実際の権限の整合［P1］

- 現状: README・ルールには管理者による代理登録があるが、通常入力と新規枠保存は本人を対象としている。ルール上の能力と、画面から到達できる操作に差がある。
- 改善: 必要な運用なら、管理者が他人の詳細から「代理で希望を登録」を明示的に選べるようにする。対象者と代理操作を保存前に表示し、履歴へ記録する。リーダーの代理登録権限を勝手に拡張しない。
- 効く理由: 管理機能を通常の本人入力から区別すると、対象者の取り違えを防ぎながら、緊急時の入力をアプリ内で処理できる。
- 完了条件: 役割別のUIとルールが一致する。本人IDの固定値で誤登録されない。不要な運用なら機能拡張せず、説明との不一致を解消する。

## 6. 追加すべき機能

### N-01 提出期間・締切・提出状況［P1、運用確認後］

- 最小仕様: 管理者が募集期間・対象者・締切を設定。本人は希望を入力後に「提出」。管理側は未提出・提出済み・提出後変更を確認する。
- 配置: 本人の入力画面上部に締切と提出状態。確定・調整画面に未提出者一覧と対象へ移る入口。
- 効く理由: 空欄だけでは「出られない」「未入力」「入力途中」を区別できない。提出を日々のシフトとは別の状態にすることで、確認の連絡と推測を減らす。
- データ案: `submissionPeriods` と期間ごとの `submissions`。提出時刻・対象revisionを保存。提出後編集は再提出が必要な状態へ変える。
- 完了条件: 全日不可でも提出できる。対象外・参加前の日を未提出として数えない。締切後の編集可否をルールで統一する。
- 未確定: 提出単位、締切後の扱い、提出を業務で使うか。自由更新運用なら「提出」導入を見送り、対象期間の入力状況だけにする。

### N-02 定型シフト・前週コピー［P1］

- 最小仕様: 個人用に「出社9–17」「午前出社・午後在宅」等の複数枠テンプレートを保存し、選択日に適用。前週コピーは内容を表示してから実行する。
- 配置: 希望入力シートに「テンプレート」、複数選択バーに「テンプレートを適用」。設定画面の奥に置かない。
- 効く理由: 種別と時間を繰り返し選ぶ作業を「再利用」に置き換えるため、入力数と転記ミスが減る。手軽さのために即時変更へ戻す必要もない。
- データ案: 個人・グループを識別した `shiftTemplates`。保存先の日付だけを変え、新規希望として作成する。
- 完了条件: 確定済みを上書きしない。既存希望にはスキップ／置換の差分を表示。6枠上限・重なり・削除済み種別を検証し、再試行で重複しない。

### N-03 確定後の変更申請［P2］

- 最小仕様: 本人が確定枠から変更希望を送信し、管理者・リーダーが承認／差し戻し。承認前は元の確定シフトを維持する。
- 配置: 確定枠の詳細に「変更を申請」。確定・調整に申請一覧と変更前後の比較。
- 効く理由: チャット上の相談とカレンダーの正本が分離する問題を減らす。未承認の希望で勤務予定が上書きされることも防ぐ。
- データ案: `changeRequests` に元枠ID・revision・変更案・状態・申請者・処理者・時刻。承認時は元枠の変更有無を検証する。
- 完了条件: 申請中に元枠が変わった場合は再確認。二重承認が起きない。理由は任意の短文とし、全員のカレンダーへ不要に露出させない。

### N-04 変更履歴と最近の変更［P1の基盤／UIはP2］

- 最小仕様: 登録・修正・確定・取消・却下を、誰が・いつ・どの枠へ行ったか記録。本人は自分、管理側は権限内の履歴を閲覧する。
- 配置: 枠の詳細に履歴。ホーム相当の上部には本人に関係する最近の変更だけを表示する。
- 効く理由: 「いつの間にか違う」を調査でき、確認の往復を減らす。変更申請・再試行・取り消しを正しく扱う共通基盤にもなる。
- データ案: `shiftEvents` に操作ID、対象、変更前後、実行者、時刻。現在値にある更新時刻だけでは過去の状態は復元できない。
- 完了条件: シフト更新と履歴記録が分離して欠落しない。一般メンバーが管理者の履歴を偽造できない。保持期間とアクセス範囲を定義する。

### N-05 必要人数・時間帯別の不足表示［P2、要件依存］

- 最小仕様: 日・時間帯・勤務種別ごとの必要人数を設定し、確定した勤務可能枠の人数と比較する。
- 配置: 日付の要約と週の時間軸。「13–15時：必要3人／確定2人」のように、押すと根拠を見られる表示にする。
- 効く理由: シフトを見る目的が人数確保なら、利用者が毎回目視で数える作業をなくせる。日単位の合計だけでは途中の不足を見落とす。
- データ案: `coverageRequirements`。同一人物の重なる枠は二重計上せず、希望・不可・却下を確定人数へ混ぜない。時間未指定の枠は扱いを定義するまで別枠集計にする。
- 完了条件: 複数枠・途中退出・勤務場所の違いに対応する。必要人数未設定を「不足0」と表示しない。
- 未確定: 人数の基準が本当にあるか、在宅を出社人数へ含めるか。基準がなければ導入しない。

### N-06 通知・リマインド［P2］

- 最小仕様: まずアプリ内で、確定・承認・締切接近を通知する。外部通知は送信先・頻度・本人の設定を決めて追加する。
- 配置: 関係する画面の案内と通知一覧。通知から該当期間・枠へ直接移動する。
- 効く理由: 利用者が定期的に全予定を見直す必要を減らせる。ただし通知を増やすだけでは確認負担が増えるため、同一操作をまとめ、本人に関係する変化に限定する。
- 依存: N-01／N-03／N-04、イベントID、既読管理、送信の重複防止。
- 完了条件: 一括確定で枠数分の通知を送らない。連携失敗を勤務未登録と誤認しない。既存のSlack運用エージェントと重複して催促しない。

### N-07 パスワード再設定［P1］

- 最小仕様: ログイン画面に「パスワードを忘れた方」を追加し、既存の認証基盤による再設定を利用する。
- 効く理由: ログインできない利用者が管理者の個別対応を待たずに復帰できる。日々の提出機能へ到達できない状態を解消する。
- 完了条件: 入力エラーと送信結果を案内し、アカウントの存在有無を過度に明かさない。今回の計画作成ではメール送信しない。

### 当面優先しないもの

- AIによる自動シフト確定: 必要人数・制約・承認責任が未定。まずN-05で人が判断できる根拠を整える。
- 個人カレンダー用CSV: ICSが既にある。CSVしか受け付けない転記先が確定した場合だけ列仕様を決めて追加する。
- アプリ内チャット・勤怠打刻・給与計算: 希望と勤務予定の管理から大きく広がるため、別の要件として扱う。
- オフラインでの無条件編集: 競合と確定状態の扱いが先。初期段階では未保存・通信状態の明示を優先する。
- カレンダー購読の再公開: 現在の非表示・既定無効の方針を尊重し、別途必要性を判断する。
- 装飾目的だけの全面配色変更・アニメーション追加: 情報構造と操作の問題を解決した後で判断する。

## 7. 実装の分割と依存関係

規模は相対的な目安であり、日数見積もりではありません。小は局所UI、中は複数画面・状態管理、大はデータやルールを含む変更です。

| 段階 | 作業 | 規模 | 前提・完了ゲート |
|---|---|---|---|
| 0 | 現行差分の引継ぎ、役割別シナリオ、改善前の操作記録 | 小 | 購読非表示と同期変更の意図を維持。比較用データを固定 |
| 1A | I-01 全枠表示・枠単位判定 | 中 | 表示切替で情報欠落0。混在状態をテスト |
| 1B | I-03 保存・再試行・選択対象、I-07 エラー表示 | 大 | 失敗と競合を再現して入力・整合性を保持 |
| 2A | I-02 詳細／編集分離、I-05 配置・密度、I-07 共通Dialog | 中 | メンバー・リーダー両方が主要課題を操作可能 |
| 2B | I-04 真の週表示、I-06 フィルター、I-08 出力確認、I-09 権限整合 | 中 | PC・スマホの表示と操作を検証 |
| 2C | N-07 パスワード再設定 | 小 | 認証用テスト環境で復帰経路を確認 |
| 3 | N-02 テンプレート、N-04 履歴基盤、N-01 提出管理 | 大 | 提出運用の要件決定。新しいルールと互換性を検証 |
| 4 | N-03 変更申請、N-04 履歴UI、N-06 通知 | 大 | 履歴・競合制御・イベント重複防止が先に完成 |
| 5 | N-05 人数比較、I-08 連携状態 | 中〜大 | 必要人数・連携状態取得方法が決定 |

最初の実装依頼は段階1A・1Bに絞り、その後のUI改修を別のレビュー単位にすることを推奨します。全面改修を1回で行うと、表示・保存・データ変更のどこで問題が発生したか切り分けにくくなります。

### 技術的な進め方

- `App.tsx` にある表示条件、選択状態、編集処理を責務ごとに切り出す。ファイル分割そのものを目的にせず、段階ごとの変更で必要な部分だけ整理する。
- 日付・人・枠の抽出と操作対象判定は純粋関数にし、一覧・月・週・書き出しで意味を揃える。
- UIの状態バッジとFirestoreの状態変更を分けて設計する。提出状態を個々のシフトの `status` に混ぜない。
- 現行の却下は勤務種別 `却下` として保存され、元の種別を残さない。将来は審査状態と勤務種別を分ける案を検討するが、既存データから元種別を推測して復元しない。
- 新規データは既存シフトをそのまま表示できる追加方式を基本にする。スキーマを変える場合は旧データ・ICS・API・Sheets同期への影響を別途検証する。
- 同期先からシフトを書き戻す双方向連携は追加しない。シフトの正本と派生データの関係を維持する。
- 権限・入力検証・履歴の保証は画面だけに置かない。Firestoreルールと必要なサーバー処理をセットで設計する。

## 8. 検証計画と完了基準

### 8.1 比較する操作課題

| 課題 | 測るもの | 成功の条件 |
|---|---|---|
| 明日の自分のシフトを確認 | 到達時間、タップ数、読み違い | 全枠と状態を正しく説明でき、書き込みが発生しない |
| 来週の3日へ同じ希望を登録 | 操作数、やり直し、保存結果 | 3日へ意図した枠だけ登録される |
| 複数人の希望をまとめて確定 | 対象理解、見落とし、結果一致 | 希望枠だけ確定し、対象外が分かる |
| 出社から在宅へ切り替わる日を確認 | 情報欠落、時間の誤認 | 全表示で同じ時間枠を把握できる |
| 保存失敗から再試行 | 入力消失、重複、復旧手順 | 入力を保ったまま1回分の結果へ復旧できる |
| Excelへ当月分を転記 | 条件理解、列ずれ | 表示された期間・状態と出力が一致する |

まず改善前の値を記録し、同じ端末・同じダミーデータ・同じ課題で比較します。効果の割合や秒数は現段階では断定しません。日常の閲覧が速くなり、入力の誤りが減ることを採用基準とします。単日入力の手数が増える場合は、複数日入力全体の負担と併せて評価します。

### 8.2 技術・画面の検証

- 純粋関数: 0／1／2〜6枠、希望・確定混在、不可、却下、未知の種別、週境界、日付範囲、操作対象の抽出。
- 保存: 連打、二重送信、途中失敗、同時編集、削除対象混在、原子的保存の範囲、履歴の整合性。
- 権限: メンバー・リーダー・管理者・退会者・他グループ。UIを経由しない書き込みも確認。
- レスポンシブ: 幅375／390／768／1280px、縦横、長い氏名、1／6／12／30人、6種別。ブラウザ内スクロールと固定バー、キーボード表示時の保存ボタン。
- アクセシビリティ: フォーカス移動、Escape、入力ラベル、色を除いても状態を区別できるか、文字拡大、前景と背景のコントラスト。
- 連携: ICSとExcelの既存形式、APIとSheetsの現行契約。新しい状態を追加する場合も、希望・確定を外部がどう扱うか確認する。
- 実装後の基本検査: 対象のVitest、`npm run lint`、`npm run build`。Worker変更時はWorkerのテストと `npm run worker:typecheck`。ルール変更時はJavaとFirestoreエミュレータを用意してルールテストを実行する。
- プレビューは閲覧以外の処理が省略されているため、保存・提出・権限の検証はAuth／Firestoreエミュレータ等で行う。
